# Flow добовление новых компонентов:

1. Создаёшь сам компонент согласно архитектуре уже в дикомпозировоном
виде
2. Добовляешь новый комопонент в storybook
3. Документируешь в @UI_KIT_DOCS.md
4. Пишешь JSDoc-комменты (`/** ... */`) над экспортируемым компонентом
и над каждым полем в его `*Props` типе — их читает
`scripts/generate-component-docs.ts` (`bun run docs:generate`) и
собирает в `docs/components.json`, это отдельный машиночитаемый
источник документации для AI-агентов, его тоже нужно поддерживать
в актуальном состоянии наравне с @UI_KIT_DOCS.md
5. запускать `make ci`

# Минимальные условия рабоы:

* используй всегда alies в проекте: 
@components, @motion, @stories, @styles, @tokens, @hooks - все они уже 
сконфигурированы в ladle, vite, tsconfig 
* Старайся по минимум использовать lib radix-ui/*, используй только в том
случаи если реализация radix-ui дейстивтельно лучше сделал, 
чем если бы мы делали
* Если ты вдрук подумаешь что ты в monorepo, то тебе показалась
* Запуск всех команд через make/bun
* Style components семантика ближе к shadcn ui к 
примеру <Tabs>, <TabsItem>, <TabsToogle>
* проверка на format & linter
* один компонент == один файл. дикомпозировать hook, model, ui, utils
* Не использовать inline игноры для linter, formater, typecheck.
  Исключение — `biome-ignore` допустим, только если:
  1. Причина обязательна к комментарию и объясняет *почему*, а не *что* (не "лишний пропс", а конкретное ограничение — семантика кастомного ARIA-виджета, ссылка на баг библиотеки и т.п.)
  2. Правило нельзя обойти без реальной архитектурной правки (например, `lint/a11y/useSemanticElements` в кастомном listbox/combobox — семантика ARIA-паттерна намеренно отличается от нативного HTML-элемента)
  3. Если одно и то же обоснование повторяется в нескольких файлах — выносить его в общий хук/утилиту с одним игнором внутри, а не копировать построчно (см. `useResetIndexOnChange`)
